Security

Defense in depth for agentic AI.

DollhouseMCP customizes AI behavior, and customizable behavior is an attack surface. The platform is built on a single hard principle: an LLM's instructions are suggestions, and the server's policies are enforcement. Everything below sits between the model and your machine.

Why agentic AI needs this

An MCP server that can read files, run commands, call agents, and pull in community content is a powerful tool and a large attack surface. The threats are not hypothetical. A persona file can carry a hidden prompt injection. A community element can attempt path traversal. A model that has been talked into ignoring its instructions can try to run a destructive command. A Unicode homograph can disguise a malicious payload as ordinary text.

DollhouseMCP assumes all of that can happen and is designed so that the model being wrong, compromised, or manipulated is not enough to cause harm. Enforcement lives in the server, where the model cannot argue with it.

The core architectural decision: every privileged operation is checked by server-side policy after the MCP client approves the tool call. "Always allow" in your client does not bypass it. The model cannot talk its way around it. The policy is the boundary.

The layers

DollhouseMCP is not a single security check. It is a stack of independent layers, each defending a different class of threat, each able to stop an operation on its own.

1. The Gatekeeper

A server-side permission engine that every MCP-AQL operation passes through. Active elements contribute allow, confirm, and deny policies; the most restrictive rule wins.

2. Danger zone enforcement

Programmatic blocking that survives restarts. When an agent crosses a danger threshold, it is blocked at the process level until verified out of band.

3. Autonomy evaluator

A multi-stage evaluation that gates every autonomous agent step: continue, pause for approval, or escalate, based on risk and reversibility.

4. Content security

Prompt-injection detection, Unicode normalization, safe YAML parsing, and regex-DoS protection applied to every piece of element content.

5. Filesystem security

Path-traversal prevention with symlink resolution, an extension allowlist, atomic locked writes, and a command allowlist for shell execution.

6. OAuth and API security

Encrypted token storage, constant-time token comparison, optional TOTP multi-factor, and token-bucket rate limiting on external calls.

7. Activation store isolation

Per-session state with validated session identifiers, a type allowlist, and integrity checks so one session cannot leak into or tamper with another.

8. CLI tool classification

Static and pattern-based risk scoring for shell commands, with a separate irreversibility flag, so dangerous and unrecoverable operations are treated differently.

1. The Gatekeeper

Every MCP-AQL operation — Create, Read, Update, Delete, Execute — passes through the Gatekeeper before it runs. The Gatekeeper resolves a permission level from a four-stage pipeline: route validation, active-element policy, cached session confirmations, and the endpoint's default policy. The hierarchy is strict. 

deny  >  confirm  >  allow  >  route default

Permission levels run from auto-approve for reads, through confirm-once-per-session for creation, to confirm-every-time for update, delete, and execute, to outright deny. Some operations — deleting an element, executing an agent, aborting execution — are marked non-elevatable: no element policy can auto-approve them. And if an element's deny list includes the confirmation operation itself, the session is locked to read-only, because the path used to grant exceptions has itself been closed.

2. Danger zone enforcement

Some situations are past the point where a confirmation prompt is enough. The danger zone enforcer is a programmatic block: when an agent crosses a danger threshold, it is recorded to disk and blocked, and that block survives a server crash or restart. Clearing it requires an out-of-band challenge — a one-time code shown through an OS-native dialog, never returned in the model's response, so a compromised model cannot read its own way out.

3. The autonomy evaluator

Higher agency has to stay bounded and observable. Before every autonomous step, the autonomy evaluator runs a multi-stage check: step-count limits, the outcome of the previous step, action-pattern matching against per-agent approve and require-approval lists, a safety-tier escalation ladder, and a numeric risk score against configurable tolerance. The outcome is always one of: continue, pause for a human, or escalate. 

autonomy:
  riskTolerance: conservative   # conservative | moderate | aggressive
  maxAutonomousSteps: 10
  requiresApproval: ["*delete*", "*production*"]
  autoApprove: ["read*", "list*"]

4. Content security

Element content is untrusted input. Before any of it influences the model, it runs a gauntlet.

  • Prompt-injection detection

    Deterministic pattern matching — not an AI classifier, which could itself be social-engineered — for system-prompt overrides, role impersonation, instruction overrides, embedded code execution, and known jailbreak phrasings. Skills may legitimately contain code patterns that would be blocked in a persona, so validation is context-aware.

  • Unicode validation

    Detection and normalization for direction-override characters, zero-width injection, mixed-script homograph spoofing, and non-printable control codes, with NFC normalization applied at the validation boundary.

  • Safe YAML parsing

    A safe schema only, with size limits and YAML-bomb detection: circular references, anchor-to-alias amplification, and oversized documents are rejected before they can detonate.

  • Regex-DoS protection

    Pattern execution runs under timeouts with complexity classification, so a crafted input cannot trigger catastrophic backtracking and hang the server.

  • Input validation and normalization

    Field-specific validation for identifiers, queries, paths, and URLs, including blocking IP-address formats that enable server-side request forgery. Every string value is normalized before downstream validation.

Content shipped inside the npm package is registered by SHA-256 hash so trusted bundled elements are not re-scanned against injection patterns they would falsely trip — but a hash mismatch after install revokes that trust immediately.

5. Filesystem security

  • Path-traversal prevention

    Every path is resolved to its real file — symlinks included — before it is checked against the allowed portfolio directories and an extension allowlist. There is no ../.. escape and no symlink redirect out of the sandbox.

  • Locked atomic writes

    Per-file locking with timeouts serializes concurrent writes and uses a write-temp-then-rename pattern, so a crash cannot leave a half-written portfolio file.

  • Command allowlist

    Shell execution is restricted to a small allowlist with no shell metacharacters, a restricted PATH, argument validation, and a default timeout.

6. OAuth and API security

  • Encrypted token storage

    GitHub tokens are validated by format, encrypted at rest with AES-256-GCM and a key derived through PBKDF2, and redacted from every log line and error message.

  • Constant-time console authentication

    The local web console uses a crypto-random bearer token stored owner-only, compared in constant time, and Unicode-normalized with a strict hex check before comparison to close a normalization-bypass class.

  • Optional TOTP multi-factor

    The console supports RFC 6238 time-based one-time passwords with backup codes for a second factor on local administrative access.

  • Rate limiting and safe downloads

    Token-bucket rate limiting with exponential backoff governs GitHub API traffic; verification attempts are limited on a sliding window; downloads enforce timeouts, size limits, and protocol allowlisting.

7. Activation store isolation

Active-element state is persisted per session. Session identifiers are regex-validated to prevent path injection, each session writes a separate, versioned activation file, only known element types are accepted, identifiers are normalized, and a corrupt or missing file starts fresh with a logged security event rather than failing open. An ephemeral mode disables persistence entirely.

8. CLI tool classification

When elements can drive external CLI tools, every command is classified before it runs. A static map and a large set of patterns sort commands into safe, moderate, dangerous, and always-blocked tiers, and assign a 0–100 risk score weighted by irreversibility, network access, out-of-scope paths, and sensitive locations.

Risk and reversibility are tracked separately, on purpose. git checkout -b feature is risky-sounding but trivially undone; git stash drop sounds routine but is irreversible. A dedicated irreversibility flag means unrecoverable operations are gated even when their raw risk score looks modest. Elements can further constrain tools with explicit allow, confirm, and deny patterns and an approval policy with its own scope and TTL. 

externalRestrictions:
  allowPatterns:   ["Read:*", "Glob:*", "Bash:git status*"]
  confirmPatterns: ["Edit:*", "Write:*", "Bash:git push*"]
  denyPatterns:    ["Bash:rm *", "Bash:sudo *"]

Supply chain and collection security

Community-contributed content is treated as untrusted until it has been validated. Every user-contributed element runs the full content-validation pipeline before it is trusted, external resources are validated on install, duplicate detection warns before redundant publishing, and GitHub uploads are validated before any community issue is created. The Collection is a shared library, not an implicitly trusted one.

Security in the build pipeline

The defenses are continuously verified, not just shipped once.

  • Static analysis

    CodeQL runs on every push and pull request and on a daily schedule across the JavaScript and TypeScript codebase.

  • Automated security audit

    A rule-based security auditor runs on every push and pull request and daily, reporting to SARIF, commenting on pull requests, and opening issues for critical findings.

  • Dependency review

    Pull requests are blocked on moderate-or-higher runtime dependency vulnerabilities.

  • Advisory monitoring

    A weekly job reconciles the dependency tree against the OSV and GitHub advisory databases, catching withdrawn advisories, new fixes, and severity reclassifications.

  • Dedicated security test suite

    A standing suite of security-specific tests covers input validation, path traversal, command injection, YAML deserialization, token handling, memory-injection, Unicode attacks, ReDoS, and OWASP Top 10 categories, runnable on its own and in pre-merge checks.

Responsible disclosure

Security reports go through GitHub private security advisories. The project commits to triage timelines by severity, publishes fixes with coordinated GHSA advisories, and provides critical fixes for the most recent supported minor versions. The full policy lives in SECURITY.md in the public repository.

DollhouseMCP makes AI behavior programmable, and it treats that power as something that has to be earned at every step. The model can be wrong. The content can be hostile. The client can be too permissive. None of that is enough on its own, because the enforcement is not in the prompt — it is in the server.
